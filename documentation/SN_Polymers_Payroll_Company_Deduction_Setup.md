# Company deduction setup and Accounts ownership

Client decision, 26 October 2026. This supersedes the Admin/Accounts setup permissions and manual scope/binding UI described in earlier payroll documents.

Accounts alone maintains company deduction setups, published statutory deduction rules and employee payroll assignments. Admin retains employee master, category/department, joining date, permanent pay structure and EPF/ESI enrolment responsibilities. Payroll review/approval roles are unchanged. Accounts opens Employee Payroll Setup directly from Payroll navigation; the component remains inside the Employee Management module, without employee-master editing or exports. Admin cannot open the setup tab or write setup APIs/RPCs.

Company deduction setup collects establishment name (existing or new), saved state, published EPF/ESI/PT rules by readable name, and applies-from date. Supporting document references are optional; actor/time and an explicit default audit description are always recorded. Saving atomically registers or reuses canonical identity and binds the selected rules. Users never enter internal codes, binding IDs or revision UUIDs. The existing state directory and Add State action on deduction-rule drafts remain available.

Only confirmed published rules for the selected state and start date are selectable. Each published revision remains bound to one canonical scope, and overlapping scheme bindings are rejected. Existing bindings are adopted only when consistent. A rule already owned by another named establishment cannot be reassigned. The setup ends at the earliest finite end date among its selected rules. Different effective dates create new immutable setup records; existing snapshots/history are not rewritten. Company units can share an establishment; department names do not automatically create statutory identities. Historical scopes remain usable through their recorded employee histories and can be adopted by an explicit company setup with matching rules.

Employee initial setup: select employees, choose company setup, choose applies-from, review and confirm. Accounts confirmation identity/date is recorded automatically. PostgreSQL clips the start to joining date, derives category applicability and enrolment from authoritative pay sources, protects existing profiles using expected version zero, and returns independent success/failure results. Missing required scheme rules cannot produce confirmed profiles. Finite company setup coverage bounds new employee profiles. There is no automatic recalculation of existing salary drafts; the UI tells users to recalculate after a change.

Individual changes retain the complete dated profile timeline and version check internally. The normal UI shows dates, setup names, confirmation and supporting history. Internal version numbers and raw JSON are removed. The complete history is preserved as immutable revisions, including legacy advisor confirmations.

Migration 139 adds a protected immutable company-setup table, selection/options/save/apply RPCs, and Accounts-only write guards. Existing read-only legacy APIs retain their historical read permissions; setup writes are Accounts-only in HTTP and PostgreSQL. Policy masters remain Admin-owned. No tax rates, category rules, salary calculation algorithms, payment actions or approval workflow semantics are changed.

## Simpler deduction-rule authoring (Accounts)

The draft editor shows dates, scheme, state, establishment, the scheme's rates and relevant ceiling, an explicit contribution wage basis, reason, and an automatic Accounts audit record. EPF shows its wage ceiling; ESI shows its eligibility ceiling; PT shows the state/month slab editor. Technical choices and component/adjustment classification are under **Advanced settings** with readable labels. Existing draft values are loaded unchanged, including rounding, custom ceilings, collection timing and evidence. Saved unsupported contribution minimum/cap values are displayed with an explicit removal action rather than silently discarded. Migration 141 subsequently retires component-based calculation and records confirmation automatically, as described below.

**Apply standard preset** is an explicit authoring action, available after choosing a supported start date. Rates and amounts remain decimal strings. Presets replace rates, ceilings, eligibility, calculation method and rounding; they preserve wage components, adjustment decisions, collection exceptions and unsupported legacy limits. Confirmation metadata is not a client input. Every Accounts save records the current actor, database date and change reason, including after changing rates or effective dates. Changing scheme creates a fresh scheme configuration and clears slabs and wage-basis selection. Date changes never silently reapply a preset; the form warns if a previously applied preset needs review.

The curated reference values, reviewed 26 October 2026, are:

- EPF standard 12% employee / 12% employer, ₹15,000 wage ceiling for supported historical dates from September 2014 through August 2026; no blanket preset for May–July 2020. From October 2026, the monthly preset uses ₹25,000. September 2026 has no preset because the reported change is within the month and this engine resolves monthly rules. A historical date range extending into the May 2020 or September 2026 transition displays a split-revision warning.
- ESI standard 0.75% employee / 3.25% employer and general ₹21,000 eligibility ceiling from July 2019. This is a monthly-engine suggestion, not a complete contribution-period eligibility implementation. Continuation, disability coverage and employee-share exemptions still require separate review.
- No national PT rate/slab preset. Accounts supplies the applicable state/month slabs.

Sources: [EPFO ceiling announcement](https://www.pib.gov.in/PressReleasePage.aspx?PRID=2314111&lang=1&reg=3), [2026 EPF standard and notified rates](https://newsonair.gov.in/central-govt-notifies-employees-provident-fund-scheme-2026/), [ESI rates effective July 2019](https://www.pib.gov.in/PressReleaseIframePage.aspx?PRID=1574520&lang=2&reg=48), [ESIC contribution and eligibility summary](https://www.esic.gov.in/attachments/publicationfile/7d5c1e6435befca342a31d9e36d40e27.pdf), [EPFO rounding guidance](https://www.epfindia.gov.in/site_docs/PDFs/MiscPDFs/ContributionRate.pdf), [ESIC revenue manual: contribution rounding](https://rohp.esic.gov.in/Publications/RevenueManual.pdf).

New drafts use calendar-month aggregation, month-start rule resolution, collection with each run, proportional allocation after unpaid salary, current-run-month treatment for included arrears, and whole-rupee monthly rounding (nearest for EPF, upward for ESI). Both incremental collection and month-end collection remain available. These engine defaults are summarized, with an explicit standard-settings reset; the Accounts save is recorded automatically and does not imply external legal approval. Bonus and arrears inclusion remains undecided until explicitly reviewed; affected calculations still block. Advance recovery uses separate deduction treatment automatically. Reimbursement remains reserved and has no authoring input.

Wage basis is required and never inferred from the preset. Monthly gross uses `PACKAGE_BALANCE` as its internal code; daily earnings use `DAILY_WAGE`. Basic, Staff Welfare and Other Fixed are retired from active configuration and calculation. A custom selection opens Advanced settings. Select additional daily wages, overtime and holiday premiums there when applicable. Stored component-based rules require a supported replacement; they are not automatically converted to gross. An empty component selection disables draft saving. Publication remains the existing future-month review/approval workflow; no historical rows or published revisions are rewritten.

## Advanced settings audit against the current engine

Implemented after migration 142 without further SQL changes:

- Contribution components change eligible wages. Gross is the ordinary salaried base; daily wages, overtime and holiday premiums are separately consumed when included. Keep this customization for relevant factory/PT rules.
- Bonus and salary-arrears inclusion are live choices. Both have supported authoring and calculation paths. Recovery is derived from advances and supports only separate deduction treatment, so it can be automatic. Reimbursement classification is reserved in configuration but has no current authoring path: the adjustment API/database allow only BONUS, SALARY_ARREARS and ADVANCE. Hide that input until the feature exists.
- Collection timing has two implemented behaviors. Incremental collection reconciles each run against prior monthly entries; month-close rejects runs ending before month end. Keep an override only if Accounts needs split/fortnightly-run control.
- Eligibility and calculation method change actual results but the standard scheme preset already determines them. Keep their engine values; normal users need not choose raw enums. Custom cross-scheme ceilings should be exceptional rather than routine fields.
- Jurisdiction conditions currently support only NONE for calculation. PROFILE_EXEMPTIONS and UNRESOLVED block; they are not usable alternatives.
- Unpaid-salary allocation supports only PROPORTIONAL_COMPONENTS when monthly base has LOP. Keep the engine rule and hide the selector.
- Included arrears support only CURRENT_RUN_MONTH; original-period contribution recalculation is not implemented. Keep the internal value and hide the selector.
- Rounding method and precision affect employee/employer contributions. Preset summaries are more useful than unrestricted choices for routine setup. MONTH and AGGREGATE currently both pass the same monthly rounding path; their dropdown adds no distinct statutory behavior. PT reads the configured slab amount without percentage rounding, although rounding metadata remains required by the shared gate.

The Advanced panel now contains four supported wage-component checkboxes, bonus and salary-arrears inclusion choices, and an optional split-run collection override. Eligibility, method, unpaid-salary allocation, arrears period and rounding are readable calculation summaries. Opening a saved rule preserves its custom settings; applying a preset or “Use standard calculation settings” explicitly resets engine defaults. Saving a typed adjustment configuration sets recovery to separate deduction treatment without changing bonus, arrears or reserved reimbursement decisions. Legacy aggregate-adjustment rules require an explicit conversion action.

## Initial historical publication — migration 143

Client decision: permit explicit initial payroll setup for recorded historical attendance, without a general UAT bypass. In publication review, select **Initial payroll setup for a past or current month**, review the refreshed impact, provide supporting approval and acknowledge. Statutory masters remain Accounts-owned; salary policies remain Admin-owned.

Migration 143 adds service-only initial-preview and initial-publication RPCs. Start dates must be a past/current month's first day. Any prior published rule for the same normalized scheme/state/establishment blocks initialization, even outside the requested dates. Global and specific salary-policy coverage are checked together. Overlapping locked salary rows block initialization (conservatively across all statutory employees because their scope is not reliably available before setup). Initial publication serializes with salary-row writes and master publication, revalidates the preview token and version, and uses the existing immutable publication audit with `initial_setup=true`. Normal publication retains its future-month restriction. The transaction-local initialization context is restored after success or failure. Existing published rules and locked snapshots are never rewritten.

Employee profiles already accept historical effective dates with today's actual Accounts confirmation date; no verification date is backdated. Company setup dates and all required scheme revisions must cover the employee interval. Existing attendance remains unchanged. Salary policies must independently cover the payroll month. Apply 143 after 142; this task only migrates the isolated test database.
