# Guided company deduction setup

Migrations 177–180 support guided drafts, combined review, atomic publication and draft listing. Accounts uses Company Deductions to create and resume setups, review rule dates and rates, and continue to employee assignment after publication.

Accounts creates one draft containing establishment, state, effective dates and selected EPF, ESI and PT rule configurations. Employee enrolment remains a separate employee-level decision. No preset silently decides a wage basis or changes a saved custom configuration.

When assigning a setup that has EPF or ESI but no PT, Accounts can pair it with a published PT setup for the same establishment. A state-specific primary setup requires a PT setup for that state. For a Pan India primary setup, Accounts selects the state that applies to the employees. The employee profile uses each scheme’s scope and the overlapping effective dates of the selected setups.

Review validates all selected rules and the company binding together, presents scheme-specific conflicts and impacts, and returns a single token covering the complete draft and relevant database state. Publication rechecks the token and authorization under the same transaction locks as existing payroll master publication and locked payroll protection. Stale reviews must be repeated.

One PostgreSQL transaction publishes all selected revisions, binds them to the company scope, creates the company setup and records audit events. Any failure rolls back all changes. A retry after a lost response must not create duplicates; design and test an idempotency key bound to the exact request and actor. Reuse existing validation and publication logic only after verifying its lock ordering and transaction semantics. Historical locked-payroll checks remain conservative; do not change them as part of this feature.

Implement Accounts-only authenticated endpoints for draft, review and publication, with strict input validation and stable scheme-specific errors. Add a forward-only migration and update RPC/schema manifests. Preserve meaningful effective dates, immutable published history and locked snapshots. Existing production compatibility is not required, but existing local UAT records must not be silently destroyed.

Verification: exercise one and multiple schemes, invalid wage bases and PT slabs, incompatible dates, historical conflicts, unauthorized actors, stale tokens, concurrent publication, duplicate retries and forced mid-operation failures proving rollback. Run isolated local DB regression and contract tests, including a payroll calculation using the resulting company setup.

## Backend design

1. **Run the existing publication checks during review.** A PostgreSQL subtransaction exercises statutory draft creation, publication, and company binding, then rolls back the writes. This keeps review aligned with the existing constraints and avoids duplicating publication logic. Temporary audit writes roll back, though PostgreSQL audit sequence numbers can have gaps. The state name comes from the state UUID. Case-variant overlaps that the existing supersession path cannot replace are blocked.
2. **Review the company binding with the rules.** Match the target scope using the same selection logic as the existing company save. Check for a setup already starting on that scope and date. For each scheme, check overlaps on the target scope after accounting for the predecessor truncation that publication will perform. Report blockers by scheme, keep warnings separate and return the earliest selected rule end date as the effective end of the setup. Support explicit historical initialization for the applicable schemes and preserve its existing restrictions.
3. **Wire the Accounts-only endpoints.** Add `POST /company-deduction-setups/guided-drafts/:id/review` and `POST /company-deduction-setups/guided-drafts/:id/publish` to the payroll router. Review takes the expected draft version and publication mode. Return `publishable`, per-scheme blockers and warnings, the scope and effective dates, and a token when publishable. Build the token from a deterministic representation of the draft ID, version and payload, actor, mode, relevant effective-date context, overlapping revisions, and company setup and binding state. Use stable error codes for stale reviews and blocked publication.
4. **Publish in one transaction.** Lock the guided draft row. For historical initialization, take the existing payroll employee table lock before the `payroll_masters` advisory lock, as migration 143 does. Hold the applicable locks through revalidation and commit. Recompute the review and verify the token before committing any master write. Save each normalized rule through the existing draft RPC, obtain its fresh per-rule token, then call the appropriate existing publication RPC. Pass the resulting revision IDs to `save_payroll_company_deduction_setup`. Let any failure abort the entire transaction, including audit writes. The old per-rule token remains internal to this operation.
5. **Record the publish result and make retries safe.** Add a protected publication receipt with one result per draft and a unique actor and idempotency key pair. Bind that key to the draft version, mode, review token and approval reference. Return the original result on an identical retry and reject key reuse for a different request. Serialize same-draft publications on the draft row and reject further edits once a receipt exists, including an edit that was already waiting for the row lock.
6. **Verify locally.** Exercise the SQL functions and the HTTP routes, including stale reviews, concurrent submissions, identical retries, and a binding failure after rule publication. Run schema and RPC contracts against the isolated stack and verify a payroll calculation with a resulting company setup.
